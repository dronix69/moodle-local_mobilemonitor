# PROMPT PARA OPENCODE: DESARROLLO DEL PLUGIN MOODLE LOCAL_MOBILEMONITOR

## 1. Rol del agente

Actúa como un desarrollador senior especializado en Moodle LMS, PHP, arquitectura de plugins Moodle, seguridad informática y desarrollo de sistemas escalables.

Tu objetivo es desarrollar un plugin de tipo `local` para Moodle llamado:

**Mobile Token Monitor (`local_mobilemonitor`)**

El plugin debe ser compatible con Moodle 4.5+ y permitir monitorear, registrar y notificar la creación de tokens asociados al servicio web `Moodle mobile web service`.

No eres un simple generador de código. Debes analizar la arquitectura de Moodle, consultar las API disponibles, implementar correctamente los componentes y verificar que el resultado cumpla los estándares oficiales.

## 2. Objetivo principal

Desarrollar un plugin que permita al administrador de Moodle conocer cuándo un estudiante genera un token de acceso para la aplicación Moodle Mobile.

El sistema debe permitir:

- Detectar automáticamente la creación de tokens.
- Identificar al usuario que generó el token.
- Identificar el servicio web asociado.
- Registrar fecha y hora de creación.
- Registrar fecha del último acceso cuando esté disponible.
- Identificar tokens asociados a Moodle Mobile.
- Notificar al administrador.
- Mantener un historial de eventos.
- Mostrar un panel de auditoría.
- Detectar patrones de generación repetitiva de tokens.

IMPORTANTE: El plugin debe funcionar sin deshabilitar Moodle Mobile ni modificar el funcionamiento normal de los servicios web.

## 3. Arquitectura técnica

Tipo de plugin: `local`.

Nombre técnico: `local_mobilemonitor`.

Nombre visible: Mobile Token Monitor.

Versión mínima: Moodle 4.5.

Lenguaje: PHP compatible con la versión mínima requerida por Moodle 4.5.

Base de datos: XMLDB de Moodle.

Interfaz: API nativa de Moodle, Bootstrap compatible con el tema y componentes estándar.

Utilizar exclusivamente las API oficiales de Moodle cuando exista una funcionalidad equivalente.

No introducir dependencias externas innecesarias.

## 4. Investigación técnica obligatoria

Antes de programar:

1. Analiza la API de eventos de Moodle 4.5.
2. Verifica la existencia y estructura de `core\event\webservice_token_created`.
3. Verifica la existencia y estructura de `core\event\webservice_token_sent`.
4. Identifica los datos disponibles en cada evento.
5. Investiga cómo obtener el servicio web relacionado con el token.
6. Comprueba cómo se relacionan los registros de eventos con la tabla `external_tokens`.
7. Verifica los campos reales de dicha tabla en Moodle 4.5.
8. Investiga el funcionamiento de los Event Observers.
9. Comprueba cómo enviar notificaciones utilizando el sistema de mensajería de Moodle.
10. Identifica las API oficiales para consultar registros y permisos administrativos.

No inventes nombres de propiedades, métodos, constantes ni estructuras de eventos.

Consulta el código fuente de Moodle 4.5 cuando sea necesario.

Si algún evento no proporciona todos los datos necesarios, utiliza una consulta segura y eficiente a través de las API de Moodle o de su capa DML.

No registres información que no puedas verificar.

## 5. Funcionalidades del plugin

### 5.1. Monitorización de tokens

Implementar un observer para detectar:

`core\event\webservice_token_created`

Cuando se produzca el evento:

- Obtener el usuario asociado.
- Obtener el identificador del token.
- Identificar el servicio web.
- Determinar si pertenece a Moodle Mobile.
- Registrar fecha y hora.
- Registrar IP cuando esté disponible y sea técnicamente fiable.
- Registrar el evento en una tabla propia.

El plugin debe identificar correctamente el servicio:

`Moodle mobile web service`

No debe confundirlo con otros servicios web personalizados.

### 5.2. Registro de eventos

Crear una tabla propia mediante `db/install.xml`.

Nombre sugerido:

`local_mobilemonitor_log`

Campos sugeridos:

- id
- userid
- tokenid
- externalserviceid
- eventtype
- ipaddress
- timecreated
- timemodified

Utilizar los tipos de datos adecuados de XMLDB.

Crear índices para:

- userid
- tokenid
- externalserviceid
- timecreated

Evitar almacenar:

- El token secreto.
- Contraseñas.
- Credenciales de acceso.
- Información innecesaria del dispositivo.

Controlar duplicados mediante una estrategia de idempotencia.

### 5.3. Panel de administración

Crear una página:

`/local/mobilemonitor/index.php`

Debe incluir:

- Total de tokens móviles registrados.
- Total de estudiantes involucrados.
- Tokens creados durante las últimas 24 horas.
- Tokens creados durante los últimos 7 días.
- Última actividad registrada.
- Tabla de eventos recientes.

Columnas:

- Estudiante.
- Nombre de usuario.
- Servicio web.
- Fecha de creación.
- Dirección IP.
- Tipo de evento.

Incluir filtros:

- Nombre del estudiante.
- Nombre de usuario.
- Rango de fechas.
- Tipo de evento.
- Servicio web.

Implementar paginación mediante las API de Moodle.

El panel debe ser intuitivo, moderno y compatible con los temas estándar de Moodle.

### 5.4. Notificaciones

Implementar notificaciones mediante el sistema nativo de mensajería de Moodle.

Permitir configurar:

- Activar o desactivar notificaciones.
- Notificar creación de tokens.
- Notificar generación repetitiva.
- Destinatarios administrativos.
- Frecuencia de notificación.

Crear una notificación administrativa que contenga:

ASUNTO:
Nuevo token Moodle Mobile detectado

CONTENIDO:
Se ha detectado la creación de un nuevo token asociado al servicio Moodle Mobile.

Información:

- Estudiante.
- Nombre de usuario.
- Servicio web.
- Fecha y hora.
- Dirección IP, cuando esté disponible.

Incluir un enlace al panel de auditoría.

Evitar enviar notificaciones duplicadas.

No enviar correos directamente mediante funciones PHP como mail(). Utilizar las API de mensajería de Moodle.

### 5.5. Detección de actividad repetitiva

Implementar un mecanismo configurable para identificar patrones sospechosos.

Ejemplo:

Un estudiante genera 5 tokens en un período de 24 horas.

El sistema debe:

- Identificar al estudiante.
- Contabilizar los eventos.
- Comparar con el umbral configurado.
- Generar una alerta administrativa.
- Evitar alertas repetidas para el mismo incidente.

El umbral debe poder modificarse desde la configuración.

IMPORTANTE: Una generación repetitiva no implica necesariamente una vulneración. El sistema debe clasificarla como actividad que requiere revisión, no como ataque confirmado.

### 5.6. Configuración administrativa

Crear:

`/local/mobilemonitor/settings.php`

Configuraciones:

- Activar monitorización.
- Activar notificaciones.
- Activar detección de actividad repetitiva.
- Umbral de tokens.
- Período de evaluación.
- Cantidad de días de retención de registros.
- Destinatarios de notificaciones.

Permitir configurar las opciones desde Administración del sitio.

### 5.7. Privacidad y protección de datos

Implementar correctamente la Privacy API de Moodle.

Crear:

`classes/privacy/provider.php`

El plugin debe:

- Declarar los datos personales que almacena.
- Permitir exportar los registros de un usuario.
- Permitir eliminar los registros asociados a un usuario cuando corresponda.
- Respetar las políticas de privacidad.
- No almacenar tokens secretos.
- No almacenar contraseñas.
- Limitar el acceso a los registros a usuarios autorizados.

## 7. Seguridad obligatoria

Aplicar todas las medidas de seguridad recomendadas por Moodle:

- Validar permisos con `require_login()` y `require_capability()`.
- Crear capacidades específicas en `db/access.php`.
- Proteger operaciones administrativas.
- Utilizar `sesskey` en operaciones que modifiquen datos.
- Escapar correctamente las salidas HTML.
- Utilizar consultas parametrizadas.
- Evitar SQL concatenado.
- Utilizar la capa DML de Moodle.
- Validar todos los parámetros recibidos.
- Evitar exposición de identificadores sensibles.
- No mostrar información de otros estudiantes a usuarios sin permisos.
- No registrar secretos de autenticación.

Crear una capacidad:

`local/mobilemonitor:viewlogs`

Asignada inicialmente a administradores.

Crear otra capacidad:

`local/mobilemonitor:manage`

Para administrar la configuración y las operaciones de mantenimiento.
